## 2. Key Gaps (ACCEPTANCE P3: double-click / late response / instance switch / disconnect)

### G1: Double-click - submit button relies on ref guard during commit await

- Location: workbench/src/pages/CapabilitiesPage.tsx:70
- Gap: Submit button disabled condition is !ready||running||!confirmed. execute(true) sets setRunning(true) at :18, but React state updates are batched - running becomes true on next render. During the prepareRun await (:20), user can click submit again before running reflects to DOM. The request.current ref guard (:17) blocks the second call - domain-level protection exists. But if ref guard is removed, UI has no second line of defense.
- Executable verification case: Load CapabilitiesPage in browser, click prepare, confirm, then double-click submit rapidly. Assert submitRun called exactly once. Current tests verify expression logic via AST extraction + evalCommitCheckExpr, not in real React render.
- Severity: MEDIUM

### G2: Late response - prepare completes after epoch changed, canCommitCapability does not check epoch

- Location: workbench/src/pages/CapabilitiesPage.tsx:16-27
- Gap: execute(commit) awaits prepareRun at :20, then calls canCommitCapability(prepared,next) at :22. canCommitCapability (capability-run.ts:14-22) compares epoch/port/token/prompt/fingerprint between prepared and next - but does NOT verify that next.epoch matches the CURRENT epoch from useLiveChat. If user disconnects and reconnects (epoch increments) while prepare is in-flight, next.epoch will match prepared.epoch (both from old connection), canCommitCapability returns true, and submitRun is called with a stale draft. The submitCapability function in useLiveChat.ts:165-168 has canSubmitCapability which checks epoch.current, providing a second gate - but this assumes submitRun actually calls submitCapability. If submitRun is wired differently, the stale draft could leak.
- Executable verification case: Start prepare, disconnect during prepare await, reconnect with new epoch, observe whether commit button remains enabled. Assert commit is blocked after epoch change.
- No current test covers this timing.
- Severity: MEDIUM

### G3: Instance switch - prepared draft survives across epoch change in CapabilitiesPage

- Location: workbench/src/pages/CapabilitiesPage.tsx:13-15
- Gap: The epoch prop (line 9) triggers useEffect at :15 which clears prepared/confirmed/running. But the prepared state is cleared via setPrepared(null) which is async - if the user clicks commit in the same render cycle before the state update flushes, the old prepared draft could be used. The request.current guard and the abort at :15 cleanup provide some protection, but the race window exists in theory.
- Executable verification case: Prepare a capability, switch instances (epoch change), immediately click commit before re-render. Assert commit is blocked.
- Severity: LOW (useEffect cleanup and request.current abort provide protection)

### G4: Disconnect during verify - approval.request race with end()

- Location: workbench/src/hooks/useLiveChat.ts:58-66
- Gap: onEvent handler checks live() (epoch guard) at :60. If approval.request event arrives in the microtask queue before end() is called (user clicks disconnect while approval is in-flight), the event could be processed before epoch increments. The live() check at :60 and session.current null check at :59 provide protection. If approval.request arrives after end() sets session.current=null but before the WebSocket close event fires, the event is dropped at :59. This is correct behavior but untested.
- Severity: LOW (live() guard and session.current null check exist)

## 3. Browser Launch Scripts - Token Exposure and Shared Log Boundary

### G5: Management token printed to stdout in test helper scripts

- Location: workbench/tests/s1-browser-launch.mjs:12, workbench/tests/s1-control-server.mjs:9
- Gap: Both scripts call console.log with JSON containing token:server.token, printing the management token to stdout in plaintext. ACCEPTANCE requires "token not left in address bar or logs". These are test helper scripts, not production code, but if stdout is redirected to a log file or shared terminal, the token leaks.
- Additional finding: The two scripts are near-identical. s1-browser-launch.mjs imports writeFile/readFile/mkdir/mkdtemp/rm/tmpdir/join but does not use them - dead imports. s1-control-server.mjs is a subset without the unused imports.
- Executable verification case: Run the script, pipe stdout to a file, grep for the token value. Assert token appears in the file.
- Severity: LOW (test helpers only, not production; but should use stderr or a named pipe for token output)

### G6: package-policy.mjs whitelist does not include review/audit records

If these review artifacts should ship with the package for traceability, the whitelist needs updating. If they are internal-only, this is correct.
