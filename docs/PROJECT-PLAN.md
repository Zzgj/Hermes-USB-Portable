## 实施原则

1. **以继承为主，不重写已经能用的原项目。** 原版启动器、便携 Runtime、Hermes CLI/TUI、Setup、Gateway 和更新入口是现有基础。
2. **优化不以“能启动”为目标，而以“能作为可审批、可取消、可诊断的运维工作台”为目标。**
3. **Hermes 可更新，不永久锁死在某个版本。** 但每次实际安装的版本和 commit 都要记录，否则无法诊断和回滚。
4. Runtime 二进制和 Hermes 源码采用不同策略：Python/Node/uv 等低频更新组件继续校验哈希；Hermes 保留用户主动更新能力。
5. 不集成本地 GGUF、llama.cpp 或内置 Ollama Runtime；模型能力来自远程 API。
6. 不执行自动磁盘格式化；真实打印机安装只能在 P3 专用测试环境中进行。

## Hermes 版本与更新策略

“记录当前版本”不等于“永久不允许更新”。本项目采用下列方式：

- **首次安装基线**：仓库记录一个已检查的 bootstrap 版本，确保新环境可重试。它不是永久上限。
- **首次安装与后续更新分开处理**：首次安装使用经审计的官方稳定 Release；后续更新复用官方 `hermes update`，其默认目标是 `origin/main`。当前官方更新器没有“自动跟随最新 Release tag”的独立稳定通道，因此项目不虚构该能力。
- **更新入口**：启动器提供独立的只读 `hermes update --check`，应用更新前先运行只读 `hermes update --plan` 并要求用户确认，最终仍由官方更新器执行。
- **不重复实现上游能力**：官方更新器已经提供默认 quick 状态快照、可选完整备份、依赖更新、配置迁移、关键文件语法验证、代码自动回退和更新回执；Portable 层只负责暴露这些能力并验证便携边界。
- **记录而非阻止**：官方更新回执保存到便携 `HERMES_HOME/logs/update_receipts/`；Portable 更新包装器另外生成不复制参数、配置或步骤详情的安全摘要，并刷新 Runtime 的实际版本、commit、通道、时间和结果，不因为 bootstrap manifest 中的旧版本而拒绝启动。
- **数据边界**：更新可以迁移 Hermes 配置和依赖，但不得把 `data/`、Profiles、Sessions、Memory、Skills 或 Obsidian Vault 移出便携目录，也不得静默丢失用户数据。

截至 2026-09-03，官方最新稳定 Release 是 [Hermes Agent `v0.21.0` / tag `v2026.8.31`](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.8.31)；当前 bootstrap 基线已是该版本。因此当前不需要把版本号改成另一个值，需要完成的是“以后可以安全更新”的流程。

## 为什么原项目已经可用，还要优化

原项目解决的是**“如何把 Hermes 放在一个目录/U 盘上直接启动”**，它在这个目标上已经很完善。本项目的新目标是**“在不破坏这个优势的前提下，把它扩展为普通用户能安全使用的 AI 运维工作台”**。

因此优化点只集中在原项目未试图解决的部分：

| 原项目已经做得很好 | Workbench 目标额外需要 |
|---|---|
| 便携 Python/Node/uv/venv 和一键启动 | 安装/更新/失败的结构化状态、诊断和回退 |
| Hermes CLI/TUI、Setup、Gateway、Doctor、Update | CLI/TUI/Desktop/WebUI/Workbench 多入口编排和健康检查 |
| `HERMES_HOME` 指向便携 `data/` | Desktop/Electron/Chromium/AppData/Temp 的实测落地审计 |
| Hermes 已支持多 Provider、Memory 和 Skills | 面向普通用户的 API/代理/Profile 可视化管理和凭据保护 |
| Hermes 能调用工具 | 适配真实工具事件、已有审批与取消，展示日志及具体恢复能力 |
| 一般文件和网络工具 | 按需接入已有工具/MCP；专用制品仓库须另行评估，不是第一版必需 |
| 终端菜单可直接使用 | Stitch Workbench 图形界面和结构化 Hermes 后端集成 |

如果某项改造不能对应到上述明确差距，或会让原版主流流程变得更差，则不应进入实现。
